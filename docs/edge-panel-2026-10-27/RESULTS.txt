Windows 11 / Edge tab-local panel — 2026-10-27

Scope and authorization
- OP5P 192.168.100.25 was unreachable from both WSL and Windows.
- The user explicitly authorized this Windows workspace as the destination
  for this change and selected an Edge-only in-page panel implementation.
- Chrome retains the native sidePanel implementation. Desktop Edge is
  detected by the Edg/ UA token before entering that implementation.

Reproduction
- Installed Microsoft Edge 156.0.4314.42, visible isolated profile.
- Loaded the extension, pinned it using Edge's own extensions menu, and
  clicked the real toolbar icon using Windows UI Automation and mouse input.
- All four user-supplied URLs reproduced the native panel disappearance.
  The page viewport was 872 CSS px with the native panel and 1258 CSS px
  after returning to the manga tab, with the panel no longer visible.
- A direct sidePanel.open call from tabs.onActivated was rejected even when
  the browser tab was selected using actual native mouse input. Reapplying
  enabled:true did not restore the native panel.
- native-before.json records the URLs, titles, viewport widths and API error.

Implementation
- Edge renders the existing panel markup and shared panel.js inside a closed
  ShadowRoot, in the extension's isolated content-script world.
- No iframe, web-accessible resource, permission increase, site script API,
  or browser-global auto-open behavior was added.
- Toolbar click toggles only that tab. Close removes the panel, not the
  ongoing translation. Returning to another tab never opens its panel.
- The same DOM retains selections and scrolling across tab switches and
  close/reopen. Session storage restores an open panel on document reload.
- Position and width can be adjusted. This is an overlay on the webpage,
  not a resized native browser viewport; readers keep their original layout.
- Existing capture covers have higher stacking order than the panel.
